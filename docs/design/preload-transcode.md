> 状态：**第一版已实现**（2026-10-13 立项并当日完工）。后端全链路（任务队列/Worker
> 协议/产物登记/派生物失效/冷数据清理/设置项/存储登记）+ 网页端入口与状态展示 +
> 独立 Windows Worker（初版 worker/preload_worker.py，2026-10-16 随统一调度 v2
> 收敛为单一程序 worker/worker.py——下文旧文件名按当时实现保留；纯标准库）已落地；本机 dev 环境用真
> ffmpeg 完成 4K HEVC → 1080p H.264 全链路验证（§8 验收清单中"人工矩阵/双端选轨/
> 抢占"等项仍待生产验收）。
> 执行端按用户拍板改为**硬件优先**（高功耗机器专门开机干活，越快转完越省电）：
> Worker 启动时探测本机 ffmpeg 能力随 claim 上报，有 NVENC + scale_cuda 走
> 全 GPU 链（硬解 → scale_cuda → NVENC，SDR 源帧不出 GPU；编码器随档位，
> 见 §2），HDR 源色调映射下载回内存走软件 tonemap（上游 ffmpeg 无 tonemapx，
> 用 hable；jellyfin-ffmpeg 的 tonemapx 探测命中时优先）再回传 GPU 编码，
> 无 NVENC 落回 libx264 软编。
> 真机验证：RTX 2070 SUPER，4K HEVC → 1080p H.264，产物 encoder tag = h264_nvenc。方向来自用户实际痛点：手头没有任何可
> 7×24 常开的低功耗实时转码设备（Mac mini 之类），唯一的强算力是高功耗 Windows 机——
> 让它常驻待命不现实，闲时批量干活才是它合理的用法；叠加外网场景下家庭上传带宽扛不住
> 原片码率。与 `remote-transcode.md`（实时远程转码 Worker，已实现）共用协议与设备授权，
> 但解决的问题、产物生命周期、调度方式都不同。
> 作者拍板记录：档位起步一档、第二档按真实使用补（§2）、HDR 必须支持（§4）、字幕内封
> （§5）、存储管理三件套（§6）、入口仅逐部/逐季/逐集手动（§3）。

## 1. 问题与定位

**痛点（两条，缺一条本设计都不成立）**：

1. **没有可常开的实时 Worker**。远程硬件转码（remote-transcode.md）要求一台待命的
   转码设备：Mac mini 待机十几瓦挂一个月无所谓，Windows 游戏主机整机待命一天就是
   上百度电——**高功耗设备与"实时待命"在经济上不成立**。手头只有 NAS（弱机，实时转码
   烤不动）和 Windows（强算力但费电），前者干不了、后者不适合"随时被叫醒"。
2. **外网场景家庭上传带宽扛不住原片码率**。即使转码算力足够，实时转出的高码率流仍要
   从家里宽带挤出去，外网卡顿的另一半在这里，实时 Worker 治不了。

预转码（本设计）把这两条一起解掉：Windows 在**本来就开着的时候**闲时批量把指定影片
转成低码率版本，长期保存为该媒体的一个可选文件版本。外网播放时 NAS 只发小文件——
不需要任何设备实时待命，NAS CPU 与家庭上传带宽同时退出瓶颈。

**与实时远程转码的分工**（能力上并存，使用上对本部署预转码是主路径）：

| | 实时远程 Worker（已有） | 预转码（本设计） |
|---|---|---|
| 设备要求 | 可 7×24 常开的低功耗转码机 | 无常开要求：高功耗机器顺路干活，干完即走 |
| 时机 | 播放的当下 | 闲时提前 |
| 触发 | 播放决策自动分配 | 用户手动逐部/逐集指定 |
| 产物 | HLS 临时分片 → NAS 转码缓存，随缓存策略过期 | 一个文件版本，长期保存，可随时删除/重新生成 |
| 解决 | 播放时刻 NAS CPU 不够 | 外网带宽不够 + NAS 完全不参与播放 |

> 若将来添置 N100 等低功耗常开设备，它实现同一协议后既可实时转码也可领预转码任务
> （§7）——本设计不给设备类型设门槛，只是不依赖"常开"这个前提。

**定位一句话**：给"常在外网看的那几部片"准备便携版本，不是库管理策略。因此**坚决不做
全量转码、不做自动补全库**——那会悄悄吃掉几百 GB，也偏离功能存在的理由。

## 2. 目标档位：档位是接口，规格随格式

**结论（2026-10-16 更新，格式维度）**：档位只有「省流/高清」两个名字（用户不接触
参数），规格由**全局编码格式**决定（设置 → 转码 → 预转码，默认 H.264）。分辨率
档位与播放页清晰度对应——产物高度 ≤ 播放页所选清晰度上限时直通/重封装命中，
**零转码**（手选清晰度从此天然会用预转产物，不需要任何隐式规则）。

| 档位 | H.264（默认） | HEVC |
|---|---|---|
| **省流**（默认 `saver`） | 480p / H.264 / AAC 192k / **1.5 Mbps**（= 播放页 480p 档） | 1080p / HEVC Main / AAC 192k / **1.5 Mbps**（原省流档原样） |
| 高清 `premium` | 720p / H.264 High / AAC 256k / **3 Mbps**（= 播放页 720p 档） | 1080p / HEVC Main / AAC 256k / **4 Mbps**（原高清档换编码，码率不动） |

- **编码器随格式**：HEVC= hevc_nvenc，H.264= h264_nvenc（软编回退恒 libx264，
  见下方"被否"——HEVC + 无 NVENC 的 Worker 会因产物编码不符被登记闸拒收）。
- **格式在下单时快照到任务行**（`preload_task.video_format`）：改全局设置不影响
  在途任务，重试/断点续转按下单时格式装配命令。
- **HEVC 的卖点**：省流档同等流量（1.5M）下清晰度更高（1080p 对 H.264 的 480p）；
  代价是 Firefox 与部分老设备不支持——这些机器播放回退服务器实时转码。两档同为
  1080p 时产物并存且都直通，起播择优取码率更高的高清档（`_best` 第三键）。
- **历史**：第一版只有高清一档（1080p H.264 4M）；上线当天补省流档（HEVC 1080p
  1.5M）并设默认。2026-10-16 引入格式维度：省流/高清名字不变，H.264 规格改为与
  播放页 480p/720p 对齐，HEVC 规格保留原两档。省流档**无直拷判定**（台账没有源
  视频码率，判断不了"已经够小"，宁可多转一次）；直拷只属于 H.264 格式的档位
  （源 ≤ 档位高度且已是 H.264/SDR = 已经是目标档）。
- **档位表达为服务端的一个枚举值**（`preset_id` × 格式变体），而不是散落的参数
  组合。再加新档只是新增枚举，UI 与协议不动。
- 体积预估按 `码率 × 时长 + 字幕/音轨开销` 计算，误差控制在 ±20% 内即可（用于 §6 的
  价格标签与配额预检）。

**被否**：做成"用户自定义码率/分辨率/编码器自由组合"——重复 arr 系统参数面板的教训，
用户不需要在转换环节再当一次参数工程师；档位由产品定义、逐版本增加。**也被否**：
档位名直接叫 480p/720p（与播放页菜单同名）——用户不必知道参数，省流/高清两个字
就够；参数差异是服务端按格式的事。

## 3. 入口与任务模型

**结论：入口只做逐部/逐季/逐集手动；任务排队、可取消、断点续转；Windows 客户端是第一个
执行端。**

- **入口**：网页端媒体详情页顶部操作排的「预转码」弹窗，下单的唯一门面（§8 显眼
  入口）：电影逐版本下单，剧集列全季分集、按季分组——整季一键下单、逐集可单转。
  文件版本列表只显示状态（已就绪 / 转码中 / 失效）与取消/重试，不放下单入口。
  入口只做在网页端
  （手机/电脑浏览器同源可用），**不进桌面客户端**（§7）：功能属于"库"，不属于某台机器。
- **任务模型**：用户在服务端下的是**任务**（target file → preset），不是直接下"转码"。
  服务端维护全局任务队列，任何在线的预转码 Worker（见 §7）都可领取。任务可取消、
  可重试；服务端重启后未完成任务按台账恢复。
- **为什么排队而不是客户端直接转**：产物必须登记回服务端成为"版本"，注册逻辑只该存在
  一份；多 Worker 领同一队列天然解决"两台电脑都想干活"的并发与去重。

**被否**：客户端本地转完手动"导入版本"——省了协议工作量，但产物指纹、去重、失败恢复
都要用户人肉保证，且第二台设备接入时逻辑要重写一遍。

## 4. HDR 源：第一版就支持（作者拍板必须支持）

**结论：HDR10 / HLG 走 ffmpeg 色调映射转 SDR 后进同一档；杜比视界（P5 交叉）按 HDR10
兼容层处理；转出的版本在详情页标注「HDR→SDR」。**

- 服务端播放转码已有成熟的色调映射路径（`ffmpeg_args.py` / `hwprobe.py`，含硬件探测与
  档位选择），预转码直接复用同一套参数构造，避免两套映射结果不一致。
- 色调映射在**闲时**执行，可以开质量优先参数（较慢的算法/较高的 crf 质量），这正是
  预转码比实时转码有优势的地方。
- 4K HDR 源默认落到 1080p SDR 档（§2 的一档）；不做"HDR 保留"档——外网移动端本就
  播不了 HDR，保留 HDR 只会产出大文件且多数播放端显示错误。

**风险登记**：色调映射效果是观感敏感项，验收要过 `remote-transcode.md` 同款的人工矩阵
（见 §8）。

## 5. 字幕与音轨：内封为主

**结论：字幕与全部音轨内封进产物（MKV）；验收标准是"内封字幕轨在网页端、桌面端播放时
可选"。**

- MKV 内封是体积、可切换性、工具链兼容的最优解；项目网页端已支持外挂/内封字幕轨道
  选择，播放端选轨 UI 是现成的。
- 烧录字幕被否：样式固化、体积增大、无法关闭，且项目已有完整的软字幕渲染链路
  （ASS 特效含 JASSUB，桌面端内置），没有理由降级到烧录。
- 图形字幕（PGS/VobSub）第一版**跳过**（不转写、不烧录，产物里不含该轨并在任务结果
  里说明）——OCR 转写是独立的大工程，不绑死本功能。音轨多选时 AAC 统一转码，原轨
  为 AAC 时直拷。

## 6. 存储管理：派生物身份 + 三件套

**核心事实：产物可再生。这一条免掉 90% 的存储管理复杂度——敢让删除按钮随处可见、
敢用最简单的配额兜底、敢让冷数据一键清。**

**产物身份**：预转码版本在库层标记为**派生资产**（derived asset），记录来源文件 ID、
preset、生成时间、大小、参数指纹。**产物文件名自带片名与码率**（complete 时按源条目
定名：`{片名} ({年份})[ SxxEyy] - {档位} {分辨率} {编码} {码率}.mkv`，如「坠落2：死点
(2026) - 省流 1080p HEVC 1.5Mbps.mkv」）——版本列表与下载直接显示文件名，不能是一个
通用占位；分段上传 URL 用固定协议名（`artifact.mkv`）避开中文文件名的 URL 编码。
由此推出两条自动规则：

- 源文件被删除/回收时，其预转码版**直接失效清理，不进回收站**（源都没了，派生物没有
  存在意义，不占第二次空间）；
- 洗版（quality-upgrade.md）换源后，旧源的预转码版自动失效，详情页提示「已因换源失效，
  可重新转码」。

**三件套**（各管一层，不发明更多策略）：

1. **总配额**（默认开）：设置页一个数字（默认取磁盘的 15% 或 200 GB 的较小值）。新任务
   排队前按体积预估预检，超配额则暂停入队并提示。这是防呆兜底——用户什么都不管，
   膨胀也有上限。
2. **手动「清理冷数据」按钮**（永远在）：预转码产物列表按最近一次播放时间排序，一键
   删除"N 天未播"的版本，执行前预览将删列表与可释放总量。N 默认 90 天，可调。
3. **自动清理开关**（默认关）：打开时复用同一条"N 天未播"规则自动执行；发生时在通知/
   活动流记一笔（「自动清理了 3 部共 22 GB」），不静默。UI 上把它放在手动按钮旁边——
   用户先点几次手动版理解了规则，再去开自动化，自动化不该是盲盒。

**价格标签**：点「转码为便携版本」时先展示预估体积（「这部约多占 8.2 GB，当前剩余
126 GB」）。可选展示省流量对比，立住价值感。

**入口展示**：缓存管理页（cache-management.md）为预转码产物加一个专属区块：当前共占
X GB / 共 Y 部 / 最老的 Z 天前，与转码缓存、回收站并列。

**被否**：LRU/LFU/按类型/按分辨率等多开关清理策略——行为不可解释，正是 quality-upgrade.md
从 arr 教训里立下的反面清单。

## 7. 执行端：独立 Worker 程序，客户端零改动

**结论：本功能是一个 server 功能。产品逻辑全部在服务端（任务队列、下单入口、配额、
版本登记、清理），执行端是照 macOS Worker 样式新写的**独立 Windows Worker 程序**，
不改 `apps/desktop/` 客户端一行代码**。检验标准：把 Windows 从架构里拿掉，功能仍完整
存在，只是暂时无人执行——这保证手机/网页随时下单看进度不依赖任何一台客户端开机，
也避免为私有功能维护桌面客户端 fork。**

- **分工**：
  - **Server（大头）**：任务队列与状态机（下单/排队/派发/取消/失败重试/重启恢复）、
    体积预估与配额预检、派生物生命周期（§6）、产物登记为版本、缓存管理页区块、
    网页端入口按钮（详情页「转码为便携版本」，网页与手机浏览器同源可用）。
  - **Windows Worker（小头）**：独立后台程序，连 NAS 领任务 → 跑 ffmpeg → 传产物。
    ffmpeg 复用桌面端打包已验证的同一套运行时清单（prepare-runtime.ps1 产出的
    mpv/ffmpeg 目录），但不打包进客户端、不共享客户端进程。
- 复用：设备授权（device-auth.md，`transcode` scope）、签名 URL 取源、产物上传、
  心跳/进度上报、并发槽位——这些实时转码已解决，不重做；macOS 实时 Worker 的协议
  实现是现成参照。
- **扩展点**（协议增量，需在 remote-transcode.md 补节）：
  1. 任务领取：Worker 上报 `role: "preload"`（与实时播放决策的池子分开），服务端按
     任务队列派发整任务（整文件），而非播放会话的滚动分片计划；
  2. 产物落点：HLS 分片改为**整文件产物**（最终 MKV/MP4），上传后由服务端校验完整性
     （时长/流数/抽样解码探针）再登记为版本——失败的任务整件作废重转，不做部分采纳；
  3. 空闲调度：任务只分给声明了 `role: "preload"` 且空闲的设备；执行中的实时播放任务
     优先级永远高于预转码（同一设备两角色时可抢占，预转码任务断点续转）。

**已知缺口（2026-10-16 记录，未实现）**：实时播放抢占让位杀掉的预转码任务不上报失败，
挂 CLAIMED 等每小时一次的 preload_maintenance 租约回收——最慢 1 小时才重派。方向 =
让位中断即回队重派（Worker 被让位时向服务端发一条「让位」上报，服务端当场回队）。
另：让位公式（并发 −1 −实时任务数）保证「只要有人在播放，预转码必停」——Worker GUI
的勾选文案已改「播放优先，转码让位」，不给「边播边转」的暗示。

- **Worker 自身设置**（它自己的界面/配置文件，不在客户端里）：并发数、「仅接通电源时
  执行」、开机自启可选。高功耗设备是间歇在线的，所以任务领取设计为"在线时领、离线
  无碍"——队列里没领走的任务自然等下一台设备上线，不需要任何设备为它待机。
- **断点续转**：ffmpeg 分段输出 + 已传段台账（复用实时转码的产物上传代理与重试语义）。
- **被否**：把执行器做进 Windows 客户端（设置页开关 + 客户端内领任务）——入口和开关
  会把客户端拖进私有功能的长期维护，且离开这台机器功能入口就没了；独立 Worker 与
  客户端解耦，上游发新客户端照装不误。

## 8. 验收清单（第一版完成线）

- [ ] 逐部/逐集在网页端下单任务 → Windows Worker 领取 → 产物登记为可选版本，网页端
      与桌面端播放前可选到它
- [ ] HDR10 源转出的 1080p SDR 版人工验收：色调映射无明显色偏/带状，对照 NAS 实时转码
      同片效果
- [ ] 内封字幕在网页端与桌面端播放时可选；多音轨可选
- [ ] 价格标签体积预估与实际偏差 <±20%；配额预检拦截超配额任务
- [ ] 源删除 → 预转码版自动消失；洗版换源 → 旧版自动失效且可一键重转
- [ ] 「清理冷数据」预览与释放量正确；自动清理（开启后）有活动流记录
- [ ] 实时播放任务与预转码任务同机抢占：播放优先，预转码断点恢复
- [ ] 缓存管理页出现预转码区块，总量统计正确
- [ ] 手机浏览器（外网）下单与查看任务进度全程可用，不依赖任何客户端开机

## 9. 明确的非目标

- 不做全量/自动补全库转码；不做任何形式的"库健康度"驱动自动转码
- 不做用户自定义参数面板（档位由产品定义）
- 不做 HDR 保留档
- 不做 PGS/VobSub 图形字幕转写
- 不在本设计内做 iOS/Android 执行端（协议就绪后自然可加）
