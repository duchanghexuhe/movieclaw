## 1. 问题与定位

**痛点（两条，缺一条本设计都不成立）**：

1. **没有可常开的实时 Worker**。远程硬件转码（remote-transcode.md）要求一台待命的
   转码设备：Mac mini 待机十几瓦挂一个月无所谓，Windows 游戏主机整机待命一天就是
   上百度电——**高功耗设备与"实时待命"在经济上不成立**。手头只有 NAS（弱机，实时转码
   烤不动）和 Windows（强算力但费电），前者干不了、后者不适合"随时被叫醒"。
2. **外网场景家庭上传带宽扛不住原片码率**。即使转码算力足够，实时转出的高码率流仍要
   从家里宽带挤出去，外网卡顿的另一半在这里，实时 Worker 治不了。

预转码（本设计）把这两条一起解掉：Windows 在**本来就开着的时候**闲时批量把指定影片
转成低码率版本，长期保存为该媒体的一个可选文件版本。外网播放时 NAS 只发小文件——
不需要任何设备实时待命，NAS CPU 与家庭上传带宽同时退出瓶颈。

**与实时远程转码的分工**（能力上并存，使用上对本部署预转码是主路径）：

| | 实时远程 Worker（已有） | 预转码（本设计） |
|---|---|---|
| 设备要求 | 可 7×24 常开的低功耗转码机 | 无常开要求：高功耗机器顺路干活，干完即走 |
| 时机 | 播放的当下 | 闲时提前 |
| 触发 | 播放决策自动分配 | 用户手动逐部/逐集指定 |
| 产物 | HLS 临时分片 → NAS 转码缓存，随缓存策略过期 | 一个文件版本，长期保存，可随时删除/重新生成 |
| 解决 | 播放时刻 NAS CPU 不够 | 外网带宽不够 + NAS 完全不参与播放 |

> 若将来添置 N100 等低功耗常开设备，它实现同一协议后既可实时转码也可领预转码任务
> （§7）——本设计不给设备类型设门槛，只是不依赖"常开"这个前提。

**定位一句话**：给"常在外网看的那几部片"准备便携版本，不是库管理策略。因此**坚决不做
全量转码、不做自动补全库**——那会悄悄吃掉几百 GB，也偏离功能存在的理由。

## 2. 目标档位：档位是接口，规格随格式

**结论（2026-10-16 更新，格式维度）**：档位只有「省流/高清」两个名字（用户不接触
参数），规格由**全局编码格式**决定（设置 → 转码 → 预转码，默认 H.264）。分辨率
档位与播放页清晰度对应——产物高度 ≤ 播放页所选清晰度上限时直通/重封装命中，
**零转码**（手选清晰度从此天然会用预转产物，不需要任何隐式规则）。

| 档位 | H.264（默认） | HEVC |
|---|---|---|
| **省流**（默认 `saver`） | 480p / H.264 / 立体声 AAC 128k / **1.5 Mbps**（= 播放页 480p 档） | 1080p / HEVC Main / 立体声 AAC 128k / **1.5 Mbps**（原省流档原样） |
| 高清 `premium` | 720p / H.264 High / 立体声 AAC 192k / **3 Mbps**（= 播放页 720p 档） | 1080p / HEVC Main / 立体声 AAC 192k / **4 Mbps**（原高清档换编码，码率不动） |

- **编码器随格式**：HEVC= hevc_nvenc（NAS 本地为 QSV/VAAPI 的 HEVC 编码器），H.264=
  h264_nvenc（无硬件时 libx264 软编）。HEVC 没有软编回退：执行者没有 HEVC 硬件编码器时
  装命令阶段就判不可执行，这一单只派给能转它的执行者（§7）。
- **格式在下单时快照到任务行**（`preload_task.video_format`）：改全局设置不影响
  在途任务，重试/断点续转按下单时格式装配命令。
- **HEVC 的卖点**：省流档同等流量（1.5M）下清晰度更高（1080p 对 H.264 的 480p）；
  代价是 Firefox 与部分老设备不支持——这些机器播放回退服务器实时转码。两档同为
  1080p 时产物并存且都直通，起播择优取码率更高的高清档（`_best` 第三键）。
- **历史**：第一版只有高清一档（1080p H.264 4M）；上线当天补省流档（HEVC 1080p
  1.5M）并设默认。2026-10-16 引入格式维度：省流/高清名字不变，H.264 规格改为与
  播放页 480p/720p 对齐，HEVC 规格保留原两档。省流档**无直拷判定**（台账没有源
  视频码率，判断不了"已经够小"，宁可多转一次）；直拷只属于 H.264 格式的档位
  （源 ≤ 档位高度且已是 H.264/SDR = 已经是目标档）。
- **档位表达为服务端的一个枚举值**（`preset_id` × 格式变体），而不是散落的参数
  组合。再加新档只是新增枚举，UI 与协议不动。
- 体积预估按 `码率 × 时长 + 字幕/音轨开销` 计算，误差控制在 ±20% 内即可（用于 §6 的
  价格标签与配额预检）。

**被否**：做成"用户自定义码率/分辨率/编码器自由组合"——重复 arr 系统参数面板的教训，
用户不需要在转换环节再当一次参数工程师；档位由产品定义、逐版本增加。**也被否**：
档位名直接叫 480p/720p（与播放页菜单同名）——用户不必知道参数，省流/高清两个字
就够；参数差异是服务端按格式的事。

## 3. 入口与任务模型

**结论：入口只做逐部/逐季/逐集手动；任务排队、可取消、断点续转；Windows 客户端是第一个
执行端。**

- **入口**：网页端媒体详情页顶部操作排的「预转码」弹窗，下单的唯一门面（§8 显眼
  入口）：电影逐版本下单，剧集列全季分集、按季分组——整季一键下单、逐集可单转。
  文件版本列表只显示状态（已就绪 / 转码中 / 失效）与取消/重试，不放下单入口。
  入口只做在网页端
  （手机/电脑浏览器同源可用），**不进桌面客户端**（§7）：功能属于"库"，不属于某台机器。
- **任务模型**：用户在服务端下的是**任务**（target file → preset），不是直接下"转码"。
  服务端维护全局任务队列，任何在线的预转码 Worker（见 §7）都可领取。任务可取消、
  可重试；服务端重启后未完成任务按台账恢复。
- **为什么排队而不是客户端直接转**：产物必须登记回服务端成为"版本"，注册逻辑只该存在
  一份；多 Worker 领同一队列天然解决"两台电脑都想干活"的并发与去重。

**被否**：客户端本地转完手动"导入版本"——省了协议工作量，但产物指纹、去重、失败恢复
都要用户人肉保证，且第二台设备接入时逻辑要重写一遍。

## 4. HDR 源：第一版就支持（作者拍板必须支持）

**结论：HDR10 / HLG 走 ffmpeg 色调映射转 SDR 后进同一档；杜比视界（P5 交叉）按 HDR10
兼容层处理；转出的版本在详情页标注「HDR→SDR」。**

- 服务端播放转码已有成熟的色调映射路径（`ffmpeg_args.py` / `hwprobe.py`，含硬件探测与
  档位选择），预转码直接复用同一套参数构造，避免两套映射结果不一致。
- 色调映射在**闲时**执行，可以开质量优先参数（较慢的算法/较高的 crf 质量），这正是
  预转码比实时转码有优势的地方。
- 4K HDR 源默认落到 1080p SDR 档（§2 的一档）；不做"HDR 保留"档——外网移动端本就
  播不了 HDR，保留 HDR 只会产出大文件且多数播放端显示错误。

**风险登记**：色调映射效果是观感敏感项，验收要过 `remote-transcode.md` 同款的人工矩阵
（见 §8）。

## 5. 字幕与音轨：按用户拍板的策略

**结论（2026-10-18 拍板）：音轨只留默认轨（配音时再加原声），统一立体声 AAC；文本字幕全部内封，
PGS 只留默认 / 库语言 / 强制三类，VobSub 跳过；字幕不进分段，拼接时从源文件整轨内封。**

- **音轨**：默认轨 = `track_policy.default_audio`（与播放端同一份策略，库语言与原始语言取自
  `track_context`）。默认轨是配音且与原声不同时，再加原声；最多两条，评论轨丢弃。统一下混成立体声
  AAC（`-ac 2`）：省流 128k、高清 192k。体积预估按实际保留的轨数计算。
  - 注意：`default_audio` 在原声存在时本来就选原声，所以多数片只留一条原声；第二条只在策略退回旧
    规则、默认轨是配音时出现。
- **文本字幕**（SRT / ASS / SSA / mov_text / WebVTT）原样内封（`-c:s copy`），ASS 特效由网页端
  JASSUB 渲染。
- **图形字幕**：PGS 只留三类——策略选中的默认字幕、库语言字幕（含简繁、双语）、强制字幕（forced
  标记）；其余丢弃。网页端用 libbitsub 渲染，不烧录。VobSub 跳过（播放器不支持）。
- **字幕不进分段**：分段用输入侧 `-ss` 切时，字幕包既不裁剪、时间戳也不跟着平移，concat 后字幕会重复、
  错位（真机实测：第二段仍带着全片的字幕包，段首的台词在第二段又出现一遍）。所以分段只含视频与音频；
  拼接时一趟 `-c copy` 把保留的字幕轨与章节从源文件整轨拷入（`final_mux_argv`），时间轴与源一致，
  段边界没有问题。端到端验证（ASS + 强制 PGS + 两条音轨，20 秒、5 段）：字幕包与源逐条一致、无重复，
  时长偏差 +0.12 秒。
- 外挂字幕、AI 字幕、片头片尾标记不复制；播放层让派生版本引用源文件的这些数据，这里不做。
- 烧录字幕仍被否：样式固化、体积增大、无法关闭，而软字幕链路已经完整。

## 6. 存储管理：派生物身份 + 三件套

**核心事实：产物可再生。这一条免掉 90% 的存储管理复杂度——敢让删除按钮随处可见、
敢用最简单的配额兜底、敢让冷数据一键清。**

**产物身份**：预转码版本在库层标记为**派生资产**（derived asset），记录来源文件 ID、
preset、生成时间、大小、参数指纹。**产物文件名自带片名与码率**（complete 时按源条目
定名：`{片名} ({年份})[ SxxEyy] - {档位} {分辨率} {编码} {码率}.mkv`，如「坠落2：死点
(2026) - 省流 1080p HEVC 1.5Mbps.mkv」）——版本列表与下载直接显示文件名，不能是一个
通用占位；分段上传 URL 用固定协议名（`artifact.mkv`）避开中文文件名的 URL 编码。
由此推出两条自动规则：

- 源文件被删除/回收时，其预转码版**直接失效清理，不进回收站**（源都没了，派生物没有
  存在意义，不占第二次空间）；
- 洗版（quality-upgrade.md）换源后，旧源的预转码版自动失效，详情页提示「已因换源失效，
  可重新转码」。

**三层自动管理**（2026-10-21 定稿，取代原先「手动删 + 自动关」的保守配置）：

每层只回答一个问题，不重叠、不发明第四种策略。

| 层 | 回答的问题 | 触发 | 默认 |
|---|---|---|---|
| **配额** | 最多占多少 | 下单时预检 | 200 GB / 磁盘 15% 取小 |
| **价值淘汰** | 空间不够时先扔谁 | 配额预检不够 | 自动，无开关 |
| **冷数据清理** | 什么该扔了 | 每小时 + 磁盘低水位 | 自动开，90 天 |

1. **总配额**：设置页一个数字。新任务排队前按体积预估预检——但**超配额不再直接
   拒绝**：先按价值淘汰（见下）腾地方，腾够了照常入队，腾不够才抛
   `PRELOAD_QUOTA_EXCEEDED` 并把真实缺口报给用户（「本单预估 1.4 GB，剩余 1.0 GB」）。
2. **价值淘汰**（`evict_for_space`）：配额不够时按分数从低到高删，直到腾出缺口。

   ```
   score = 播放场次 / (1 + 距上次播放天数)
   ```

   一周前播过一次（1/8 ≈ 0.13）排在一小时前播过五次（5/1.04 ≈ 4.8）之后、
   三个月没播的（1/91 ≈ 0.011）之前。一个公式、无权重旋钮——「行为可解释」是
   本节拒绝 LRU/LFU 多开关策略的同一条理由。从未播过的按生成时间算。

   两条硬规则优先于分数：
   - **正在被转码会话读的产物永不淘汰**（`files_in_use()`）——删掉正在播的文件
     等于把用户踢出去，与播放侧 `_evict_export_for_local` 的「播放优先」同一取舍；
   - **同一条目至少留一个产物**——一季几十集全删光，用户点开又要从头等转码，
     比多占几百 MB 更糟。只剩一个时宁可如实拒绝这一单。
3. **冷数据清理**：按「N 天未播」删除（N 默认 90 天，可调），每小时跑一次；
   磁盘剩余低于 `disk_floor_percent`（默认 10%）时**立刻**跑一次价值淘汰，不等定时任务。
   后一条与自动清理开关无关：预转码与数据库同卷，盘满会让 SQLite 写不进去，
   这是「不清理就出事」的兜底。清理发生时活动流记一笔（「自动清理了 3 部共 22 GB」）。

**手动「清理冷数据」按钮**保留（永远在）：它会给出将删列表与可释放总量的预览，
用于「我知道我要删什么」的场景；三条自动路径复用它同一套判据。

**价格标签**：点「转码为便携版本」时先展示预估体积（「这部约多占 8.2 GB，当前剩余
126 GB」）。可选展示省流量对比，立住价值感。

**逐行产物预览与集中管理**（2026-10-20 拍板）：

- **下单弹窗的每一行展示的是产物，不是源**：成品文件名（与 complete 落盘同名，如
  「奥德赛 (2026) - 省流 480p H.264 1.5Mbps.mkv」）+ 预计体积，源规格退到第二行的
  尾缀（「· 源 4K · HDR10 · 17.28 GB」）做对照。切档位即重取，整屏一次批量拉
  （`POST /preload/preview`，与 `/estimate` 同一套选轨与预估口径）。
- **不能下单的行直接给原因**（「源已是便携档，无需转码」「原盘目录暂不支持预转码」
  「源文件已进回收站」）：灰掉下单键而不是让人点下去才吃 400；整季批量也只收能转的。
- **设置 → 转码的任务列表默认折叠成一行摘要**（「N 个进行中 · 共 M 条记录」），展开后
  先给 20 条、按「显示更多」往上加；进行中的永远置顶。行标题也是产物名。
- **已完成的单子就地可删产物**：这一页是预转码产物的集中管理处，删完任务转「已失效
  （可重新转码）」、概览数字同步刷新，不用再去详情页点一次。

**入口展示**：缓存管理页（cache-management.md）为预转码产物加一个专属区块：当前共占
X GB / 共 Y 部 / 最老的 Z 天前，与转码缓存、回收站并列。

**被否**：LRU/LFU/按类型/按分辨率等多开关清理策略——行为不可解释，正是 quality-upgrade.md
从 arr 教训里立下的反面清单。

## 7. 执行端：NAS 本地是正经执行者，Windows Worker 是加速器

**结论（2026-10-18 拍板）：NAS 本地转码是基石——远程 Worker 不是每个人都有，也不是时刻在线。NAS 与
Worker 跑同一套分段协议。有能转这一单的 Worker 在线时，NAS 不接新单，让 GPU 清队；没有时 NAS 接单。
播放优先：NAS 上任何播放转码会话一开始，预转码立即让位。**

- **执行者**
  - **NAS 本地**：命令走 NAS 实测的硬件链（QSV / VAAPI，能力来自 `hwprobe` 自检：原生 tone-map、
    HEVC 编码器、`tonemapx` 是否可用），解码留在 GPU。HDR 有原生 tone-map 就用原生，没有就走 CPU
    `tonemapx`（解码帧下载→映射→回传 GPU 编码）。没有硬件也接单（2026-10-20 拍板：NAS 本地是基石，
    不是每家都有 Worker，Worker 也不总在线）：H.264 用 libx264 软编，本机 ffmpeg 有 `tonemapx` 时 HDR
    也在 CPU 上做色调映射，没有就留给 Worker。慢（进度与剩余时间在活动页可见），但播放优先照旧——
    有人播放就让位，所以不会拖慢家里看片。
  - **Windows Worker**（外置，GPU）：NVENC 链，协议与 NAS 相同（`worker/*`）。Worker 自身设置（并发、
    仅接通电源时执行、开机自启）在它自己的界面里。
- **本机的三条禁忌（2026-10-20 真机踩实，前两条与实时链同一口径）**
  - **HDR 源不要因为 BT.2020 就退回软件段**：原生 tone-map（`tonemap_vaapi=…:t=bt709:m=bt709:p=bt709`）
    本身就把画面落到 BT.709，再叠 `colorspace` 转换既多余又致命——它是软件滤镜，必须先把硬件帧
    `hwdownload` 回来，整链从 GPU 直通退化成 CPU 转码。真机 4K HDR10 因此只有 **0.05× 实时**；
    去掉多余转换后 **2.2×**（约 40 倍），DV P8 1.4×。NVENC 链 10-14 就修过同一个坑
    （`_gpu_filters` 的 tone-map 分支不插 colorspace），本地 VAAPI/QSV 一直漏着。
    软件段只该在「要 tone-map 但本机没有原生滤镜」或「SDR 源要色彩空间转换」时出现。
  - **纯硬件帧链不写输出侧色彩标签**：`-colorspace/-color_primaries/-color_trc/-color_range` 只加在
    帧落回内存的软件段上。4K DV P5 源走 `tonemap_vaapi → scale_vaapi → h264_vaapi` 时，这组标签会让
    ffmpeg 7.1 在首帧重建滤镜图、插进来的软件 `auto_scale` 接不上硬件帧，整链以「Impossible to
    convert … / -38」当场崩（退出码 218，工程上表现为三次秒失败后熔断）。产物的色彩标签由帧属性
    继承，颜色不受影响（实测去掉标签后产物仍是 bt709 三件套）。
  - **杜比视界 P5 本机不接**：VAAPI/QSV 的 `tonemap_vaapi` 不认 RPU，P5 的 IPTPQc2 基础层硬转出来
    整片偏紫/发绿（同帧 RGB 实测与 `tonemapx` 差一个数量级）。装配层直接判「本机不可执行」回队等
    带 NVENC + `tonemapx` 的 Worker——与播放端 `plan.py` 的 `dolby_vision == "apply"` 同一判定。
    P7/P8（基础层就是 HDR10）不受影响，走整链 GPU。
- **这台 NAS 的实测速度（4K 源，省流档 480p/H.264）**：SDR 1080p ~14×、HDR10 4K **2.2×**、
  DV P8 4K **1.4×**、仅缩放不 tone-map 5.1×（即瓶颈是硬件 tone-map，不是解码）。
  DV P5 本机不接。2 小时电影在 4K HDR 上约 55–85 分钟转完，符合「闲时后台干」的定位。

- **失败要退避，不能立刻重派**：本地执行失败回队后按 attempts 退避（30s → 120s）。看门狗每 2 秒派
  一轮，不退避的话确定性故障 5 秒就烧满三次熔断线（2026-10-20 真机：21:24:36/38/40），瞬时抖动也
  会被当成坏源判死。「本机装不出命令」不算失败（一次 ffmpeg 都没跑），以 `yielded` 语义回队、
  不累加熔断计数，否则等 Worker 的几分钟会把它攒到熔断线。

- **分段协议**（两端一致）：视频与音频按 `SEGMENT_SECONDS` 分段，每段一个 ffmpeg 进程（`-ss` 插在
  `-i` 前，`-t` 插在输入之后，末段转到 EOF）。段文件直接落进任务目录，推进 `resume_parts`，中断后
  续转。拼接、字幕内封、探测、登记由服务端的 `finalize_artifact` 统一完成，两端共用。
- **HEVC 格式**：要求执行者有 HEVC 硬件编码器（NAS：经自检的 `hevc_qsv` / `hevc_vaapi`；Worker：
  `hevc_nvenc`）。没有就在装命令时判为不可执行，只派给具备能力的执行者。软编 HEVC 太慢，不做。
- **调度规则**
  1. 有能转这一单的 Worker 在线（且未排空）时，NAS 不接**新单**，让 GPU 按顺序清队，NAS 留给家里播放。
  2. 没有可用 Worker（离线、能力不符、排空）时，NAS 接单。
  3. **已有分段的任务归产出它的执行者**：`worker_device_id` 为空即归 NAS。被播放让位、或租约到期回队
     后，只回到同一执行者续转——不同编码器产出的分段不能混拼。
  4. NAS 已在跑的任务跑完为止，不中途交给 Worker。
- **播放优先（让位）**：看门狗每 2 秒看一次本机播放转码会话（档 ≥ 音频转码；远程会话与离线导出不算）。
  有播放在跑，本地预转码立即让位：杀掉当前段的 ffmpeg，删掉半截段，任务回队（断点保留、不计失败次数）；
  段与段之间也先检查。播放全部结束后，看门狗续派。
- **让位后立即回队并立刻重派（2026-10-18）**：让位**不是**「等租约到期再回收」。两端各自负责一半：
  - **Worker 端**：让位时停掉分段并向服务端上报 `preload.yielded`，本地工作目录原样保留；
  - **服务端**：收到 `preload.yielded` → 当场把任务退回队列（`_requeue_yielded_preload`，在途记账同步
    释放）→ 立即 `trigger_dispatch()` 派一轮。让位的这台此刻余量为 0，派单自然跳过它，任务由别的
    Worker 接手；**本机播放结束时** `_release_job` 发现这台 Worker 空出来了，再触发一次派单，把任务
    派回来从断点续转。

  所以「播放结束 → 预转码续转」的等待是**两次派单触发之间**（毫秒级），而不是 `LEASE_SECONDS`
  （10 分钟）或 `preload_maintenance`（每小时）——那两条只是 Worker 卡死、没上报 `preload.yielded`
  时的兜底路径。判据在 `tests/api/test_preload_yield.py::test_yield_requeues_task_at_once_and_releases_account`。
- **取源：边下边转（2026-10-20）**。Worker 的 `-i` 直接指向 NAS 的取源端点，转码与网络传输并行，
  不再先整文件下完再转——省掉的就是「源体积 ÷ 内网带宽」那段串行等待（29GB 源在千兆上约 4~5 分钟）。
  可行性实测：**服务端真实 argv**（HDR 源 → `tonemap_cuda` + `h264_nvenc` 480p）经 HTTP 直读该端点
  跑整段，`speed=5.93x`、产物完整、退出码 0；顺序读与中途 `-ss` 寻址各约 3.4~3.8 秒，取源不是瓶颈。
  两个必要的配套：① 给 ffmpeg 补网络自愈输入选项（`-reconnect*`、`-rw_timeout`，与实时路径同口径）；
  ② ffmpeg 会读 `http_proxy`，内网地址必须进 `no_proxy`（否则流量被代理接管，实测直接连不上）。
  输入打不开（凭据过期、端点不支持 Range）时自动**回落整文件下载**再转，不把「读不了源」变成任务终态
  失败；`MOVIECLAW_WORKER_STREAM_SOURCE=0` 可整体关掉（排查用）。NAS 本地执行者仍走本地路径。
- **进度与活动页**：本地执行每段写 `task.progress`（第几段 / 总段数、剩余时间、本段耗时）；Worker 取源
  阶段另写 `speed_bps` 与下载期 `eta_seconds`（1 秒窗口滑动平均，瞬时值抖动太大）。活动页进行中的卡片
  标明执行者（「NAS 本地」或 Worker 设备名）与当前段。
- **三个进度阶段与上报时机（2026-10-20 修）**：`downloading` → `transcoding` → `finalizing`。
  **`finalizing` 必须主动上报一次、且上报线程要活到 `complete` 返回**——收尾是「只发生一次」的状态，
  按上报周期轮的话它基本发不出去，活动页会一直挂着最后一段，看着像卡死（实测缺陷，两端都踩过：
  Worker 端写完 `finalizing` 立刻停上报线程；NAS 本地执行者干脆不写这个阶段）。
  另外拼接期间持续上报 = 持续续约：concat 是分钟级大活（上限 1 小时），不续约会被 10 分钟租约
  判超时、任务重排，白拼一次。
  上报周期 `PROGRESS_SECONDS = 15`（原 60 秒）：边下边转之后一集 37 分钟的片子十几分钟就转完，
  60 秒一拍会让段号/速度半分钟才动一次；与活动页 15 秒轮询同频，端到端最坏延迟 ≈ 30 秒。
  文案（三阶段各自的措辞）收敛在网页端 `apps/web/lib/preload-progress.ts`，`finalizing` 单独成句
  「拼接登记中」，不会被段号分支抢走。
- **被否**：把执行器做进 Windows 客户端（入口与开关会把客户端拖进私有功能的长期维护）；NAS 只做兜底
  （远程不在线时才转，基石地位与「不是每个人都有 Worker」矛盾）。

## 10. 待实现：自动生成（2026-10-21 立项，本期不做）

**结论：先记为设计，不进第一版。** 自动管理已有三层（§6），但它们只回答「留什么、
删什么」。还有一层没做：**转什么**。

### 为什么需要

现在的入口是「用户逐部/逐季/逐集手动下单」——§3 明写的取舍，也是 §9「不做自动补全」
的边界。但这个取舍有个代价：用户知道「外网随时会看」的那些片，得先想到去下单。
而真人不会提前想：剧集是一集接一集看的，今天看 E01，明天多半看 E02。

### 提议：只做「浅预取」，不做「预测」

```
用户在详情页给 E01 下单      → 自动把 E02、E03 排队（深度 2）
用户播了 E01 的预转码产物    → E02 提到队首，补 E04
```

三条约束：

1. **只跟同一条目的相邻集**，不跨条目、不看「口味」。不做推荐算法——那是
   `quality-upgrade.md` 反面清单里的同类东西，行为不可解释。
2. **深度固定 2 集**，不做「按季全部展开」。一季几千集的剧，深度 2 只是
   两个文件的成本；全季展开就是几百 GB。
3. **默认关**，与 §6 里另外三层相反：清理是「省空间」（删错还能重转），
   生成是「占空间」（转错白占）。开关放在预转码设置区，文案写明深度。

### 为什么现在不做

- 缺口还没有被证明：手动下单够不够用，要看真实使用数据；
- 它会和 §9 的「不做自动补全库」擦边——先把边界写死（深度 2、同条目、
  默认关），再实现，比实现完再吵边界便宜；
- 真要做时，它应该复用 §7 的任务队列，不新增调度路径。

- [ ] 关掉开关后不再自动排队；已在队列里的不受影响
- [ ] 深度上限不可超过 2（硬编码，不给用户调）
